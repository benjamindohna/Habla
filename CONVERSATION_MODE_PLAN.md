# Conversation Mode — Implementation Plan

Branch: `segments3-conversation`

This document describes the full set of changes to add: per-user accounts in a real database, a topic-selection home screen with LLM-generated interest tiles, and a chat-style conversation mode that re-uses the existing correction primitives. The build is split into phases so each can land and be tested independently.

---

## 1. Goal

After login, the user lands on a Spanish greeting and a 3×3 grid of interest tiles. Tiles are LLM-generated from the user's stored interests (5 matching, 3 adjacent, 1 random), pre-rolled in pairs so re-rolling is instant. Tapping a tile opens a chat: the AI opens in level-adjusted Spanish, the user records replies, and each turn re-uses the existing correction stack (interpret → localize → segment → explain) inline. Tap-to-translate works on the AI's Spanish too. Words the user looks up are stored on the user record, sorted by Spanish frequency.

---

## 2. Decisions

Resolved:

- **Native language is per-user.** Dropdown removed from UI. Seed `admin@habla.app` with `native_language = 'German'`.
- **Level is per-user, 0–100, defined linearly by capability** (see §3.6). Seeded per user; no settings UI yet. Conversation targets `userLevel + 5..+10`, narrowed to `+3..+5` below level 20 and widened to `+8..+12` above 80.
- **Corrections shown for every user turn.** Each user message renders the correction UI (localized version, segment alignment, tap-to-explain) inline.
- **TTS on AI bubbles** — confirmed. Re-uses existing `/api/tts`.
- **Conversation persistence** — store messages in DB for later review and so the system can extract interests from them when the chat ends.
- **Topics** — vague or specific is fine ("football", "Champions League", "Johan Cruijff's philosophy"). Generated each time from the user's interests array. The AI does **not** read past conversations directly; instead, when a chat ends an extraction step harvests topics-discussed from the message log and appends them to the user's interests. Future tile generations grow naturally from there.
- **Re-roll budget** — 4 sets total per home-screen visit (1 initial + 3 re-rolls). All four sets must contain disjoint topics. Re-roll button greys out after the 4th set is shown. Preload pattern: keep 1 set queued at all times; on re-roll, swap and request the next; after 4 sets generated, no further request. See Phase 4.

Still open:

1. **Deployment target.** SQLite (`better-sqlite3`) works on a local Node server (zero ops, file-based) but **not** on Vercel/serverless (ephemeral filesystem). If you'll deploy to Vercel, switch to **LibSQL/Turso** (SQLite-compatible, HTTP-backed, generous free tier). Plan below assumes local SQLite; the swap is one file (`lib/db.ts`) if needed.
2. **"Done" vs "Continue" button.** I'm assuming `Continue` = process this turn & AI replies; `Done` = end the conversation and return to the topic grid. Confirm or correct.

## 3. Architecture decisions

### 3.1 Database: SQLite via `better-sqlite3`
- `npm i better-sqlite3` + `npm i -D @types/better-sqlite3`
- DB file: `data/habla.db` (gitignored). Initialised on first server boot via `lib/db.ts`.
- Synchronous API → no `async` ceremony in route handlers.
- Single writer, fine for single-user sessions; WAL mode for safe concurrent reads.
- Migration strategy: a single `lib/schema.sql` executed idempotently on boot (no migration framework needed at this scale).

### 3.2 ORM / query layer
- **No ORM.** Raw SQL with thin typed wrappers in `lib/db.ts`. App is small; an ORM is overhead. Revisit if schema grows past ~6 tables.

### 3.3 Schema (v1)

```sql
-- users: replaces lib/users.ts
CREATE TABLE IF NOT EXISTS users (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  email           TEXT NOT NULL UNIQUE,
  password_hash   TEXT NOT NULL,
  native_language TEXT NOT NULL DEFAULT 'German',
  level           INTEGER NOT NULL DEFAULT 30,         -- 0..100
  interests_text  TEXT NOT NULL DEFAULT '',            -- free-form summary, regenerated by LLM
  created_at      INTEGER NOT NULL DEFAULT (strftime('%s','now'))
);

-- structured interest tags, one row per tag
CREATE TABLE IF NOT EXISTS user_interests (
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  interest   TEXT NOT NULL,
  added_at   INTEGER NOT NULL DEFAULT (strftime('%s','now')),
  PRIMARY KEY (user_id, interest)
);

-- words the user has looked up; freq_rank lets us sort cheaply on read
CREATE TABLE IF NOT EXISTS user_unknown_words (
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  word       TEXT NOT NULL,                             -- normalized lowercase
  freq_rank  INTEGER,                                   -- lower = more frequent. NULL if unknown.
  looked_up  INTEGER NOT NULL DEFAULT 1,                -- count
  last_seen  INTEGER NOT NULL DEFAULT (strftime('%s','now')),
  PRIMARY KEY (user_id, word)
);

-- conversations + messages (only if Q7 = yes)
CREATE TABLE IF NOT EXISTS conversations (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  topic       TEXT NOT NULL,
  created_at  INTEGER NOT NULL DEFAULT (strftime('%s','now'))
);
CREATE TABLE IF NOT EXISTS messages (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  conversation_id INTEGER NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  role            TEXT NOT NULL CHECK (role IN ('ai','user')),
  text_es         TEXT NOT NULL,                        -- Spanish content (AI: full reply; user: corrected version)
  user_raw        TEXT,                                 -- user's actual transcript, only for role='user'
  segments_json   TEXT,                                 -- cached translations / alignment
  created_at      INTEGER NOT NULL DEFAULT (strftime('%s','now'))
);
```

### 3.4 Sorting unknown words by relevance
- **Decision: assign rank on insert; sort on read.** No 24h job needed.
- Use a static Spanish frequency list shipped with the repo (`lib/freq/es.txt` — top ~50k words; ~1 MB). On insert, look up `freq_rank` and store it. Sorting unknown words is then `ORDER BY freq_rank ASC NULLS LAST, last_seen DESC`.
- Source list: any standard Spanish frequency corpus (e.g. OpenSubtitles-derived). No LLM call needed for sorting.

### 3.5 Session / auth
- Keep current bcrypt + JWT cookie scheme. `lib/auth.ts` and `middleware.ts` mostly unchanged.
- Replace the `USERS` array lookup with a `getUserByEmail()` DB call. JWT payload changes from `{ email }` to `{ userId, email }`.

### 3.6 Level definitions (0–100, linear by capability)

The dial is linear in *capability*, not in *time-to-attain*. The AI uses the level to calibrate vocabulary, grammar complexity, sentence length, and abstractness. Conversation aims `level + 5..10` (narrowed below 20, widened above 80) — based on Krashen's *i+1* hypothesis.

| Level | Description |
|---|---|
| **0** | Absolute beginner. Knows zero words. Cannot parse any sentence. AI must use single concrete nouns. |
| **10** | ~50 high-frequency words (hola, sí, no, gracias, agua, comer, casa, día). Cannot form sentences. Understands very short greetings only. |
| **20** | ~500 words. Present tense only. Can ask "where is X", "I want Y". Misses any conjugation past present. ~CEFR A1. |
| **30** | ~1,500 words. Present + simple past (pretérito). Forms 6–8 word sentences. Understands slow speech on familiar topics. ~CEFR A2. |
| **40** | ~3,000 words. All major tenses, subjunctive emerging. Comfortable in concrete daily topics; abstract topics still hard. Lower B1. |
| **50** | ~5,000 words. Full subjunctive, conditional, complex clauses. Can hold a 10-minute chat on any familiar topic. Upper B1. |
| **60** | ~7,000 words. Discusses opinions, hypotheses, personal narratives fluently. Slips on register and idiom. Lower B2. |
| **70** | ~10,000 words. Comfortable with most idioms, varied registers, complex argument. Upper B2. |
| **80** | ~15,000 words. Reads literature without dictionary. Discusses abstract topics (philosophy, politics, science) confidently. C1. |
| **90** | ~25,000 words. Near-native fluency. Subtle humour, irony, regional variation. Occasional non-native cadence. Lower C2. |
| **100** | Educated native speaker. Sophisticated political and literary register. Vast active vocabulary. No errors. |

These descriptions are inlined into the LLM system prompt for `/api/converse/start` and `/api/converse/turn` so the AI knows what each band means.

### 3.7 Greeting verb rotation

The home greeting `¿De qué quieres hablar hoy?` rotates the verb each visit so users get passive synonym exposure (Claude-Code-style rotating verbs, but pedagogical). Stored as a static list in `lib/greetings.ts`. Generated once via LLM (or curated by hand) — every entry must be (a) grammatically valid in the slot, (b) semantically reasonable, (c) flagged with a register tag (`neutral | casual | playful | regional | formal`) so we can weight selection.

Sample seed list (will be expanded to ~40–60 entries):

| Verb | Register | Note |
|---|---|---|
| hablar | neutral | default |
| charlar | casual | chat / chitchat |
| conversar | neutral | converse |
| platicar | regional (LatAm) | chat |
| dialogar | formal | dialogue |
| comentar | neutral | comment on |
| debatir | formal | debate |
| discutir | neutral | discuss |
| parlotear | playful | chatter |
| cotillear | casual (ES) | gossip |
| chacharear | playful | natter |
| departir | formal/literary | converse |
| tertuliar | playful (ES) | hold a tertulia |
| rajar | slang (ES) | yap |

A `pickGreetingVerb(level)` helper biases toward `neutral` for low levels, opens up `playful`/`regional` once `level ≥ 40`, and only picks `formal`/`literary` at `level ≥ 60`. Returned with a tiny tooltip ("rajar = informal: to chat") on hover so the learning is explicit when desired.

### 3.8 Post-chat interest extraction

When a conversation ends (`Done` button or navigating away), fire `POST /api/conversations/:id/extract`. This:
1. Reads the message log.
2. Calls `gpt-4o-mini` with a prompt: *"What concrete topics did this user actively engage with? Return 1–4 short noun phrases suitable as future conversation tiles."*
3. Upserts those into `user_interests` (deduplicates on insert) and regenerates `users.interests_text`.

This is the **only** way the AI's understanding of the user grows. Future tile generation reads `user_interests` — never the raw chat log. Keeps tile generation cheap and the user's interest profile auditable.

### Phase 3 — Topic generation API (5-3-1, no-overlap)
*Goal: tiles come from an LLM call shaped by the user's interests, with no overlap across the 4 sets shown in a single home-screen visit.*

- Create `POST /api/topics` taking `{ exclude: string[] }` (already-shown topics in this visit) and reading the user from session. Returns 9 topic strings: 5 directly matching the user's interests, 3 adjacent/related, 1 random. Order randomised server-side.
- LLM: `gpt-4o-mini`, `response_format: json_object`. Prompt explains the 5-3-1 split, accepts vague-or-specific phrasing ("Champions League", "Johan Cruijff's philosophy", "Formula 1 in 2026"), and is told to **avoid** any topic from the exclusion list (and avoid near-duplicates of them). Topic phrasing is in the user's native language (so the home screen reads naturally pre-chat).
- Returns `{ topics: [{ text, kind: "match"|"related"|"random" }] }`.
- Wire `home` to fetch `/api/topics` on mount with `exclude: []` and render the result.

**Files:** `app/api/topics/route.ts` (new), `app/page.tsx` (wire fetch), `components/TopicGrid.tsx` (props update).

**Done when:** every page load shows nine LLM-generated tiles tailored to the seeded user's interests.

---

### Phase 4 — Re-roll + preloading (4-set budget)
*Goal: instant re-rolls, no overlap across sets, button greys out after the 4th set.*

- Per home-screen visit, support up to **4 sets** of 9 topics each (1 initial + 3 re-rolls). All 36 topics are disjoint within the visit.
- State held in `app/page.tsx`:
  - `sets: TopicSet[]` — every set generated this visit (used as the exclusion list).
  - `currentIndex: number` (0..3) — which set is visible.
  - `next: TopicSet | null` — preloaded next set.
  - `rerollsRemaining: number` (3..0) — initial 3, decremented on each re-roll.
- On mount: fetch set 0 with `exclude=[]`, render it, then fire-and-forget fetch set 1 with `exclude=set0` into `next`.
- On re-roll click:
  - Reject if `rerollsRemaining === 0`.
  - Swap `next → current`, push it into `sets`, increment `currentIndex`, decrement `rerollsRemaining`.
  - If `rerollsRemaining > 0`: fire next `POST /api/topics` with `exclude = flatten(all sets so far)` to refill `next`. If `rerollsRemaining === 0`: skip the preload — the budget is exhausted.
- Re-roll button visual states: enabled (default), spinner (if user re-rolls before `next` lands — rare), greyed-out when `rerollsRemaining === 0` (with tooltip: "no more topics this round").
- Visit ends (and the budget resets) when the user enters a chat or reloads the page.

**Files:** `app/page.tsx` (state mgmt), `lib/hooks/useTopicQueue.ts` (new — encapsulates the queue + exclusion logic).

**Done when:** initial load is instant, three re-rolls are instant, the 4th press is rejected, and the 36 topics shown across the visit are all distinct.

**Files:** `app/api/me/interests/route.ts` (new), `lib/users.ts` (add upsert), `app/page.tsx` (call before nav).

**Done when:** picking a tile that's not already a match permanently shifts future tile generation toward that topic.

### Phase 7 — Conversation turn loop
*Goal: real back-and-forth with an LLM.*

- New `POST /api/converse/start` taking `{ topic, level }` → returns `{ text_es, segments }` for the AI's opener. Segments = pre-translated chunks for instant tap-to-translate (saves a round-trip per tap). Level shapes vocabulary/length.
- New `POST /api/converse/turn` taking `{ conversationId, userTextEs }` → returns `{ text_es, segments }`. Receives the **corrected** user Spanish (i.e. `local_version_es` from the existing localize step), keeps a server-side conversation history (or rebuilt from DB messages — see Q7).
- The chat flow on each user turn:
  1. Record → transcribe (existing).
  2. interpret → localize → segment (existing) → render correction in user bubble.
  3. POST `/api/converse/turn` with `local_version_es` → render new AI bubble.
- Persist every AI and user message to the `messages` table after each turn.
- `Done` button → soft-end the conversation, fire `POST /api/conversations/:id/extract` (see §3.8) to harvest topics into `user_interests`, then route back to home (which will now see updated interests).
- AI prompts include the level description from §3.6 and the target band (`level + 5..10`).

**Files:** `app/api/converse/start/route.ts` (new), `app/api/converse/turn/route.ts` (new), `app/api/conversations/[id]/extract/route.ts` (new), `lib/conversations.ts` (new — DB helpers), `components/ConversationView.tsx` (wire turn handler + Done flow).

**Done when:** can hold a multi-turn Spanish conversation with corrections shown for every user turn, and ending a chat updates the user's interests array.

## 6. Order of work

The order below is chosen so that every phase has a working app at its end, no phase is built blind against a missing dependency, and rework on previously-shipped phases is minimised.

### 6.1 Dependency map

```
Phase 1 (DB + users)
  ├──► Phase 2 (home shell, static tiles)
  │      ├──► Phase 3 (LLM tiles, 5-3-1)
  │      │      └──► Phase 4 (preload + 4-set budget)
  │      ├──► Phase 5 (interest tracking on tile-tap)
  │      └──► Phase 6 (chat shell)
  │             └──► Phase 7 (chat loop)
  │                    └──► Phase 8 (unknown-words capture)
  └──► (messages, conversations, user_interests, user_unknown_words tables — all required by 5/7/8)

Phase 9 (polish) follows everything.
```

### 6.2 Recommended sequence

1. **Phase 1** — DB + user model swap-in
2. **Phase 2** — home-screen shell with static tiles
3. **Phase 3** — LLM tile generation (5-3-1)
4. **Phase 4** — preloading + 4-set budget
5. **Phase 5** — interest tracking on tile-tap
6. **Phase 6** — chat shell (UI only)
7. **Phase 7** — chat loop (turn API + persistence + Done-extracts-interests)
8. **Phase 8** — unknown-words capture
9. **Phase 9** — polish (TTS on AI bubbles, greeting verb rotation, cleanup)

### 6.3 Why this order

- **1 must come first.** Every later phase reads or writes per-user data. Building features against the old `USERS` array and migrating later means redoing the same work twice.
- **2 before 3.** A static-tile home screen lets us validate layout, routing, and `/api/me` without LLM cost or async edge cases. Once that's solid, 3 swaps in real tiles by changing one fetch — low risk.
- **3 before 4.** Preloading is pure client-state on top of a working endpoint. Building 4 against a placeholder API means rebuilding the queue logic when the real shape (exclusion list, 5-3-1 kinds) lands.
- **4 before 5.** Either order works, but 4 is a pure UX win that's testable in isolation, while 5 only manifests as drift in *future* tile generations (slow to verify). Shipping 4 first gives an instantly noticeable improvement and frees Phase 5 to focus on the write-path correctness.
- **5 before 6.** Strictly optional — they're independent — but doing 5 first means by the time the chat shell exists, the home screen is feature-complete, and Phase 6 can ship without distraction. Also: tapping a tile in Phase 6 needs to write to `user_interests` for the round-trip to feel real, and Phase 5 already provides that.
- **6 before 7.** Phase 6 builds the UI shell with a hardcoded AI opener and routes user turns through the existing correction pipeline. This proves the layout and bubble structure work before we wire the live conversation API. Building 7 first would mean shipping endpoints with nothing to call them.
- **7 before 8.** Phase 8 captures tap-to-translate events from the chat. Without a working chat, there's nothing to instrument.
- **9 last.** Polish items (TTS on AI bubbles, greeting verb rotation) are independent of the data flow and slot in cleanly once the rest works.

### 6.4 What gets *worse* if you reorder

- **Doing 5 before 3.** Tiles are still static placeholders, so taps write meaningless rows to `user_interests`. Cleanup costs nothing but is annoying.
- **Doing 6 before 2 stabilises.** Two refactors of `app/page.tsx` in flight at once → merge headaches.
- **Doing 7 before 6.** API contracts get designed without UI feedback; almost always wrong on first try.
- **Doing 8 before 7.** Have to mock a conversation flow to verify; throwaway work.
- **Skipping Phase 1's seed step.** Login route flips to DB lookup against an empty table → instant lockout.

### 6.5 Sub-order within Phase 1 (critical)

Order matters here — if you flip steps 3 and 4, login breaks the moment the route changes.

1. Add `better-sqlite3` dep, `data/` to `.gitignore`, `lib/schema.sql`, `lib/db.ts` (boots cleanly with no users).
2. Add `lib/users.ts` rewrite (`getUserByEmail`, etc.) — does not yet replace anything.
3. Write `scripts/seed.ts`, run `npm run seed` → DB now has the 5 users with correct hashes, plus admin's German + level + interests.
4. **Verify** with `sqlite3 data/habla.db 'SELECT email, native_language FROM users;'` before touching the auth route.
5. Switch `app/api/auth/login/route.ts` and `lib/auth.ts` from the static `USERS` import to `getUserByEmail()`. JWT now carries `userId`.
6. Test login end-to-end with each seeded user.
7. **Only then** delete the static `USERS` array from the old `lib/users.ts`.

### 6.6 Sub-order within Phase 7 (critical)

This phase touches the most live state. Build it incrementally so a failure in any one step isolates cleanly.

1. Add `messages` and `conversations` tables (already in Phase 1 schema, so this is a no-op if Phase 1 was done right).
2. Build `lib/conversations.ts` with create/append/list helpers.
3. Build `POST /api/converse/start`. Test with `curl` against a hardcoded `userId` and `topic`. Verify the AI opener respects the level band.
4. Build `POST /api/converse/turn`. Test with `curl`, sending a fake `local_version_es`. Verify continuity (responses reference earlier context).
5. Wire the chat UI to call `/start` on tile-tap, then `/turn` per user submission. The UI still uses Phase 6's hardcoded opener as a fallback so failures are visible.
6. Wire message persistence — verify rows appear in `messages` after each turn.
7. Build `POST /api/conversations/:id/extract`. Test with `curl` against a finished conversation row. Verify `user_interests` gets new rows.
8. Wire the `Done` button to call `extract` then route home.
9. Confirm: returning home after a chat shows updated interests; the next tile set reflects them.
10. **Only then** remove the hardcoded opener fallback from Phase 6.

### 6.7 Verification gate before each next phase

Before starting phase N+1, the previous phase should:

- Build cleanly (`npm run build`).
- Pass a manual smoke test of the new feature end-to-end.
- Leave the previous flows working (Phase 1 ⇒ login still works; Phase 6 ⇒ home tiles still work; etc.).
- Have any new endpoints exercised at least once via the UI, not just `curl`.

### 6.8 Open-question impact on the start

- **Q1 (deployment)** — only matters at deploy time. Phase 1 can start regardless; the swap to LibSQL/Turso, if needed, is one file (`lib/db.ts`).
- **Q2 (Done vs Continue)** — only blocks Phase 6. Phases 1–5 are unblocked.

So **Phase 1 is unblocked and can start now.**
